Zustand essentials

Q1 Why use Zustand instead of Context + useReducer? +

Zustand gives a tiny global store with less boilerplate, selective subscriptions, and no provider nesting. It scales better than broad context updates for frequently changing state.

Q2 How do you avoid unnecessary re-renders in Zustand? +

Use selector functions so components subscribe only to required slices: useStore(s => s.user.name). Avoid selecting full objects unless needed; combine with shallow compare for object selectors.

Q3 How do async actions work in Zustand? +

Actions can be async functions inside the store. Call API, then set with loading/data/error updates. Keep race conditions in mind and track request id/abort when needed.

Q4 How do persist middleware and hydration impact app startup? +

Persist reads from storage during hydration. Until hydration completes, default values may render first. For critical auth/theme flows, gate UI with a hydrated flag to prevent flicker.

Q5 When should Zustand not be your first choice? +

If you need strict event-sourcing/devtools conventions across a very large team, Redux Toolkit may provide stronger structure. For server-state, prefer dedicated tools like TanStack Query.
